## 1. Контекст и цель

Сейчас слои формально разделены (`Domain ← Application ← Infrastructure ← API`), но по смыслу архитектура нарушена:

- Вся бизнес-логика лежит в `Infrastructure/Services/*` (`AuthService`, `QuizService`, `AnimeService`, …), а `Application` содержит только интерфейсы и DTO. `AddApplication()` пустой.
- `AuthService` обращается к `AppDbContext` напрямую и смешивает его с `IUnitOfWork`.
- `JwtService` — конкретный класс без интерфейса, читает `IConfiguration` и падает поздно (`int.Parse(config[…]!)`).
- Ошибки — это `KeyNotFoundException`/`InvalidOperationException`; «email уже занят» отдаёт 400, а не 409.
- Любой зарегистрированный пользователь может изменять каталог (Anime/Song/Artist/Tag/Franchise/AnimeEntry): роль админа есть в токене, но не проверяется.
- Логика интервальных повторений (`QuizService.ApplyReview`) — набор «магических чисел» внутри сервиса; сущности анемичные.
- Квиз на каждый запрос загружает все песни и весь прогресс пользователя и фильтрует в памяти.
- Нет тестов, CI, health-эндпоинта, не-root пользователя в Docker; миграции применяются при старте.

**Цель:** привести backend к целевой архитектуре из `CLAUDE.md` и `.claude/rules/backend-clean-arch.md`, закрыть дыру с авторизацией, сделать ключевую логику тестируемой и подготовить почву для мультиплеера (серверный авторитет, рейтинг). **Результат считается успешным**, когда все 9 частей из раздела 11 выполнены, поведение API не изменилось там, где это не оговорено, а границы слоёв проверяются автоматически.

## 2. Пользователи и сценарии

- Как **разработчик**, я хочу, чтобы бизнес-логика жила в `Application`/`Domain` и тестировалась без БД, чтобы безопасно менять её и добавлять мультиплеер.
- Как **владелец проекта**, я хочу, чтобы изменять каталог могли только админы, чтобы обычные пользователи не портили данные.
- Как **пользователь**, я не должен заметить изменений в работе квиза и входа, кроме понятных сообщений об ошибках и необходимости один раз войти заново (см. часть 2, открытый вопрос Q2).
- Как **член команды**, я хочу получать работу небольшими PR с понятным описанием, чтобы их можно было ревьюить.

## 3. Функциональные требования

Работа разбита на 9 частей (каждая — отдельная ветка и PR). Порядок важен.

0. **Страховка: тесты.** Создать `backend/tests/` с проектами `Domain.Tests`, `Application.Tests`, `Api.IntegrationTests` (xUnit, FluentAssertions, NSubstitute; интеграционные — `WebApplicationFactory` + Testcontainers PostgreSQL). Написать тесты, **фиксирующие текущее поведение**: `QuizService` (в т. ч. `ApplyReview`), `AuthService` (регистрация, логин, refresh, logout), ключевые эндпоинты каталога.
1. **Перенос сервисов.** Переместить сервисы из `Infrastructure/Services` в `Application/Services` (кроме `AuthService` и `JwtService`). Реализовать `AddApplication()`. Поведение API не меняется.
2. **Аутентификация без утечек.** `AuthService` → `Application`; завести `IRefreshTokenRepository`; `JwtService` → `ITokenService` (интерфейс в `Application`, реализация в `Infrastructure`); настройки JWT через типизированные `Options` с проверкой при старте; refresh-токены хранить хешем.
3. **Ошибки.** Доменные исключения (`NotFoundException`, `ConflictException`, `ValidationException`, `ForbiddenException`) + единая обработка через `IExceptionHandler` с `ProblemDetails`; «email уже занят» → 409.
4. **Авторизация.** Политика `AdminOnly` на все изменяющие операции каталога; `ICurrentUser` вместо дублирующихся `GetUserId()` в контроллерах; ограничение частоты запросов на эндпоинты аутентификации.
5. **Доменная модель.** Правила интервальных повторений вынести в доменный сервис/сущность с именованными параметрами вместо магических чисел; пересмотреть публичные сеттеры там, где это защищает инварианты.
6. **Производительность квиза.** Убрать загрузку всех песен и прогресса на запрос; фильтрация, сортировка и пагинация в БД; регистронезависимый поиск через `EF.Functions.ILike`; типобезопасная сортировка вместо строк; убрать лишний `GetByIdAsync` после сохранения. Индексы — по результатам анализа `db-engineer` (миграция — через `/db-migration`).
7. **Эксплуатация.** Health-эндпоинт; Swagger только вне Production; миграции не на старте в Production (отдельный шаг деплоя); обработка forwarded headers за прокси; не-root пользователь в `Dockerfile`; `docker-compose.yml` (PostgreSQL + API + frontend) для запуска одной командой; структурированное логирование.
8. **Frontend.** Токен читается при каждом запросе (а не один раз в конструкторе); обновление по 401; удалить мёртвый код отмены запросов; единый стиль путей в `service/api.ts`; обработка 403 и `ProblemDetails`; убрать шаблонные файлы из `public/`.

## 4. Критерии приёмки

Общие для **каждой** части:

- **Given** ветка с изменениями, **When** запускаются `dotnet build backend` и `dotnet test backend`, **Then** обе команды завершаются без ошибок и предупреждений.
- **Given** изменённая часть, **When** выполняется `/review`, **Then** нет замечаний уровня blocker/major.
- **Given** PR, **When** его открывает ревьюер, **Then** описание объясняет что и зачем, ссылается на эту спеку и содержит план проверки.

Специфичные:

| Часть | Проверяемый критерий |
|---|---|
| 0 | `dotnet test backend` запускает ≥ 1 проект тестов; тесты `QuizService.ApplyReview` покрывают границы позиций и каждую ветку расчёта |
| 1 | В `Application.csproj` нет ссылки на `Infrastructure`; поиск `AppDbContext` по `backend/src/AnimeQuizTrainer.Application` ничего не находит; все прежние тесты зелёные без правок ожиданий |
| 2 | В `Application` нет `AppDbContext` и `IConfiguration`; `ITokenService` и `IRefreshTokenRepository` объявлены в `Application`; запуск с неполной конфигурацией JWT падает **при старте** с понятным сообщением |
| 3 | Повторная регистрация одного email → HTTP 409 с `ProblemDetails`; несуществующий ресурс → 404; формат ошибок единый на всех контроллерах |
| 4 | Пользователь без роли админа получает 403 на POST/PUT/DELETE каталога (интеграционный тест на каждый контроллер); админ — 2xx; чтение каталога доступно как раньше |
| 5 | Параметры расчёта вынесены в именованные константы/настройки; поведение совпадает с тестами из части 0 (или отличия явно согласованы) |
| 6 | Число SQL-запросов и объём загружаемых данных на запрос квиза не растут с числом песен (проверяется тестом/замером, результат приложен к PR) |
| 7 | `docker compose up` поднимает рабочую связку; `GET /health` → 200; в Production Swagger недоступен |
| 8 | Вход, обновление по 401 и выход работают в браузере; `npm run typecheck && npm run lint` без новых ошибок |

## 5. Edge cases и ошибки

| Ситуация | Ожидаемое поведение |
|---|---|
| Перенос ломает регистрацию зависимостей (DI) | Приложение не стартует → обнаруживается тестом запуска `WebApplicationFactory` и сборкой |
| После хеширования refresh-токенов (часть 2) в БД лежат старые токены | Все действующие сессии становятся недействительными; пользователи один раз входят заново (Q2) |
| Смена кода ошибки 400 → 409 (часть 3) | Frontend должен обработать новый код; согласовать с частью 8 и проверить формы входа/регистрации |
| AdminOnly (часть 4): нет ни одного админа | Каталог нельзя изменять, пока админ не назначен; нужен способ назначения (Q1) |
| JWT-настройки в Production отсутствуют | Приложение не стартует с понятной ошибкой (поведение уже есть для ключа — не ослаблять) |
| Рефакторинг случайно меняет результат `ApplyReview` | Тесты из части 0 краснеют; изменение расчёта допустимо только с явного согласия владельца |
| В процессе обнаружен посторонний баг | Записать в отчёт/issue, не чинить внутри текущей части |

## 6. Нефункциональные требования

- **Поведение:** части 0–2 и 5 — без изменения внешнего поведения API (кроме отмеченного в разделе 5).
- **Качество:** предупреждения компилятора = ошибки (уже включено); новая логика — с тестами; границы слоёв проверяются автоматически (архитектурный тест или проверка ссылок проектов).
- **Безопасность:** секреты только из окружения; refresh-токены хешируются; админские операции защищены политикой.
- **Производительность:** запрос квиза не зависит линейно от общего числа песен (часть 6).
- **Наблюдаемость:** единый формат ошибок, health-эндпоинт, структурированные логи без персональных данных.

## 7. Влияние на систему

- **Данные/БД:** часть 2 — изменение формата хранения refresh-токенов (миграция); часть 6 — возможные индексы (миграция). Все миграции — через `/db-migration`, к не-локальной БД не применяются без явной просьбы владельца.
- **API:** коды ошибок (400 → 409 и др.) и формат тела ошибки (`ProblemDetails`); новые 403 для не-админов; новый `/health`. Маршруты и успешные ответы без изменений.
- **UI:** часть 8 — обработка 403/ошибок и обновление токена; визуально интерфейс не меняется.
- **Безопасность/права:** политика `AdminOnly`, ограничение частоты запросов на аутентификацию, хеширование refresh-токенов.

## 8. Вне скоупа

- Внедрение CQRS/MediatR, смена ORM или СУБД.
- Новые пользовательские функции, мультиплеер, рейтинг (только подготовка архитектуры).
- Полная переработка фронтенда и смена способа хранения токенов (переход на httpOnly cookie — отдельное решение/ADR).
- Выбор хостинга и настройка CI/CD (отдельные фазы плана).
- Автоформатирование всего репозитория (`style: format`).

## 9. Открытые вопросы
