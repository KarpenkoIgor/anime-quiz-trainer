## 1. Контекст и цель

Сейчас слои формально разделены (`Domain ← Application ← Infrastructure ← API`), но по смыслу архитектура нарушена:

- Вся бизнес-логика лежит в `Infrastructure/Services/*` (`AuthService`, `QuizService`, `AnimeService`, …), а `Application` содержит только интерфейсы и DTO. `AddApplication()` пустой.
- `AuthService` обращается к `AppDbContext` напрямую и смешивает его с `IUnitOfWork`.
- `JwtService` — конкретный класс без интерфейса, читает `IConfiguration` и падает поздно (`int.Parse(config[…]!)`).
- Ошибки — это `KeyNotFoundException`/`InvalidOperationException`; «email уже занят» отдаёт 400, а не 409.
- Любой зарегистрированный пользователь может изменять каталог (Anime/Song/Artist/Tag/Franchise/AnimeEntry): на всех мутациях стоит голый `[Authorize]`, `AddAuthorization()` без политик (`Program.cs`). Админство в токене — строковый claim `isAdmin="true"/"false"` (`JwtService.cs`), а не роль, и нигде не проверяется; `IsAdmin` никто не выставляет.
- Логика интервальных повторений (`QuizService.ApplyReview`) — набор «магических чисел» внутри сервиса; сущности анемичные.
- Квиз на каждый запрос загружает все песни и весь прогресс пользователя и фильтрует в памяти.
- Нет тестов, CI, health-эндпоинта, не-root пользователя в Docker; миграции применяются при старте.

**Цель:** привести backend к целевой архитектуре из `CLAUDE.md` и `.claude/rules/backend-clean-arch.md`, закрыть дыру с авторизацией, сделать ключевую логику тестируемой и подготовить почву для мультиплеера (серверный авторитет, рейтинг). **Результат считается успешным**, когда все 10 частей из раздела 11 выполнены, поведение API не изменилось там, где это не оговорено, а границы слоёв проверяются автоматически.

## 2. Пользователи и сценарии

- Как **разработчик**, я хочу, чтобы бизнес-логика жила в `Application`/`Domain` и тестировалась без БД, чтобы безопасно менять её и добавлять мультиплеер.
- Как **владелец проекта**, я хочу, чтобы изменять каталог могли только админы, чтобы обычные пользователи не портили данные.
- Как **пользователь**, я не должен заметить изменений в работе квиза и входа, кроме понятных сообщений об ошибках и необходимости один раз войти заново (см. часть 2, открытый вопрос Q2).
- Как **член команды**, я хочу получать работу небольшими PR с понятным описанием, чтобы их можно было ревьюить.

## 3. Функциональные требования

Работа разбита на 10 частей, пронумерованных 0–9 (каждая — отдельная ветка и PR). Порядок важен и **не совпадает с нумерацией**: часть 9 (.NET 10) выполняется сразу после части 0 (см. раздел 11).

0. **Страховка: тесты.** Создать `backend/tests/` с проектами `Domain.Tests`, `Application.Tests`, `Api.IntegrationTests` (xUnit, AwesomeAssertions — бесплатный форк FluentAssertions, т. к. v8+ платная; NSubstitute; интеграционные — `WebApplicationFactory` + Testcontainers PostgreSQL). Пакеты добавляются в `backend/Directory.Packages.props`; `TreatWarningsAsErrors` действует и на тестовый код. Написать тесты, **фиксирующие текущее поведение**: `QuizService` (в т. ч. `ApplyReview`), `AuthService` (регистрация, логин, refresh, logout), ключевые эндпоинты каталога. В тестах `ApplyReview` зафиксировать: формулы (Forgot: gap `max(3, N·0.05)`, EF −0.30, мин 1.3; Hard: `max(5, N·0.12·EF)`, EF −0.15; Medium: `max(10, N·0.20·EF)`, EF без изменений; Easy: `max(20, N·0.50·EF)`, EF +0.10, макс 4.0), что gap считается по **старому** EF, отсутствие `default` в `switch`, `ReviewCount++` после `ApplyReview`. Обновить `backend/Dockerfile` (он копирует только 4 csproj + sln перед restore и сломается от тестовых проектов) и проверить `.dockerignore`.
1. **Перенос сервисов.** Переместить сервисы из `Infrastructure/Services` в `Application/Services` (кроме `AuthService` и `JwtService`); статический `SongService.ToDto` переезжает вместе с ними. Реализовать `AddApplication()`. Поведение API не меняется. Границы слоёв закрепляются автоматически (архитектурный тест, см. Q6).
2. **Аутентификация без утечек.** `AuthService` → `Application`; завести `IRefreshTokenRepository`; `JwtService` → `ITokenService` (интерфейс в `Application`, реализация в `Infrastructure`); настройки JWT через типизированные `Options` с проверкой **всех** значений (`SecretKey`, `Issuer`, `Audience`, сроки) при старте; проверку ключа из `Program.cs` перенести без ослабления. Refresh-токены хранить хешем: детерминированный SHA-256 (не BCrypt — нужен поиск по значению), поле `Token` → `TokenHash` с сохранением уникального индекса, сырое значение возвращается клиенту отдельно от сущности. Формат admin-claim (строка или роль) решить здесь же, чтобы разлогин всех пользователей совпал с единственной сменой формата токена.
3. **Ошибки.** Доменные исключения (`NotFoundException`, `ConflictException`, `ValidationException`, `UnauthorizedException`, `ForbiddenException`) + единая обработка через `IExceptionHandler` с `ProblemDetails`; «email уже занят» → 409; `Unauthorized` → 401 (login и refresh; фронтенд обновляет токен по 401), `Forbidden` → 403.
4. **Авторизация.** Политика `AdminOnly` на все изменяющие операции каталога (на существующем `IsAdmin`; выдача админов — отдельная спека, см. §8); `ICurrentUser` вместо дублирующихся `GetUserId()` в контроллерах; ограничение частоты запросов на эндпоинты аутентификации.
5. **Доменная модель.** Правила интервальных повторений вынести в доменный сервис/сущность с именованными параметрами вместо магических чисел; пересмотреть публичные сеттеры там, где это защищает инварианты.
6. **Производительность квиза.** Убрать загрузку всех песен и прогресса на запрос (сейчас `GetAllByUserAsync` и `songs.GetAllAsync` с фильтрацией в памяти; уже существующий, но неиспользуемый `ProgressRepository.GetAvailableAsync` фильтрует в SQL — переиспользовать); убрать `songs.CountAsync` на каждый review; фильтрация, сортировка и пагинация в БД; регистронезависимый поиск через `EF.Functions.ILike` вместо `Contains`; типобезопасная сортировка вместо строкового `switch`; пересмотреть `EF.Functions.Random()` с двойным `Include`; убрать лишний `GetByIdAsync` после сохранения. Гонка при `QuizPosition++` на отслеживаемом `User` (нет concurrency token) — оценить и решить в этой части или вынести отдельной задачей. Перед удалением `ISongRepository.GetAllAsync` проверить всех вызывающих. Индексы — по результатам анализа `db-engineer` (миграция — через `/db-migration`).
7. **Эксплуатация.** Health-эндпоинт; Swagger только вне Production; миграции не на старте в Production (сейчас `Database.Migrate()` безусловно) — отдельный шаг деплоя; обработка forwarded headers за прокси (сейчас `UseHttpsRedirection` без них); не-root пользователь в `Dockerfile`; `docker-compose.yml` (PostgreSQL + API + frontend) для запуска одной командой; структурированное логирование. Учесть существующий `railway.json`. CI (`.github/workflows/` пуст) — вне скоупа.
8. **Frontend.** (Уже сделано командой в PR #6–#9: токен читается из `authStore` при каждом запросе вместо однократного чтения в конструкторе; перепроверить перед работой.) Обновление по 401; удалить мёртвый код отмены запросов; единый стиль путей в `service/api.ts`; обработка 403 и `ProblemDetails`; убрать шаблонные файлы из `public/`.
9. **Платформа: переход на .NET 10.** `TargetFramework` `net9.0` → `net10.0` (в `Directory.Build.props`), пакеты в `Directory.Packages.props` (EF Core, Npgsql.EntityFrameworkCore.PostgreSQL, JwtBearer и др.) — на версии для .NET 10; `global.json`, если есть; базовые образы `backend/Dockerfile` (`sdk`/`aspnet` 9.0 → 10.0); `railway.json`/хостинг при необходимости; упоминания «ASP.NET Core 9 / EF Core 9» в `CLAUDE.md`, `backend/CLAUDE.md`, `docs/`. Выполняется **сразу после части 0** (тесты — страховка от регрессий) и **до** части 1, отдельным PR, без изменения поведения и без попутных рефакторингов. Новые предупреждения компилятора/анализаторов, появившиеся с SDK, исправляются минимально; существующие миграции не редактируются (новую миграцию создавать только если EF 10 этого требует — через `/db-migration`). Перед работой агент проверяет актуальные версии пакетов и breaking changes (context7 / официальные release notes), а не полагается на память.

## 5. Edge cases и ошибки

| Ситуация | Ожидаемое поведение |
|---|---|
| Перенос ломает регистрацию зависимостей (DI) | Приложение не стартует → обнаруживается тестом запуска `WebApplicationFactory` и сборкой |
| После хеширования refresh-токенов (часть 2) в БД лежат старые токены | Все действующие сессии становятся недействительными; пользователи один раз входят заново (Q2) |
| Смена кода ошибки 400 → 409 (часть 3) | Frontend должен обработать новый код; согласовать с частью 8 и проверить формы входа/регистрации |
| AdminOnly (часть 4): нет ни одного админа | Каталог нельзя изменять, пока админ не назначен; нужен способ назначения (Q1) |
| JWT-настройки в Production отсутствуют | Приложение не стартует с понятной ошибкой (поведение уже есть для ключа — не ослаблять) |
| Рефакторинг случайно меняет результат `ApplyReview` | Тесты из части 0 краснеют; изменение расчёта допустимо только с явного согласия владельца |
| В процессе обнаружен посторонний баг | Записать в отчёт/issue, не чинить внутри текущей части |

## 6. Нефункциональные требования

- **Поведение:** части 0–2 и 5 — без изменения внешнего поведения API (кроме отмеченного в разделе 5).
- **Качество:** предупреждения компилятора = ошибки (уже включено); новая логика — с тестами; границы слоёв проверяются автоматически (архитектурный тест или проверка ссылок проектов).
- **Безопасность:** секреты только из окружения; refresh-токены хешируются; админские операции защищены политикой.
- **Производительность:** запрос квиза не зависит линейно от общего числа песен (часть 6).
- **Наблюдаемость:** единый формат ошибок, health-эндпоинт, структурированные логи без персональных данных.

## 7. Влияние на систему

- **Данные/БД:** часть 2 — изменение формата хранения refresh-токенов (миграция); часть 6 — возможные индексы (миграция). Все миграции — через `/db-migration`, к не-локальной БД не применяются без явной просьбы владельца.
- **API:** коды ошибок (400 → 409 и др.) и формат тела ошибки (`ProblemDetails`); новые 403 для не-админов; новый `/health`. Маршруты и успешные ответы без изменений.
- **UI:** часть 8 — обработка 403/ошибок и обновление токена; визуально интерфейс не меняется.
- **Безопасность/права:** политика `AdminOnly`, ограничение частоты запросов на аутентификацию, хеширование refresh-токенов.

## 8. Вне скоупа

- Внедрение CQRS/MediatR, смена ORM или СУБД.
- Новые пользовательские функции, мультиплеер, рейтинг (только подготовка архитектуры).
- Полная переработка фронтенда и смена способа хранения токенов (переход на httpOnly cookie — отдельное решение/ADR).
- Выбор хостинга и настройка CI/CD (отдельные фазы плана).
- Автоформатирование всего репозитория (`style: format`).
- Выдача и управление админами/модераторами (базовый админ, делегирование прав) — отдельная спека; здесь только политика `AdminOnly` на существующем `IsAdmin`.
- Выбор UI-библиотеки фронтенда (предложение shadcn/ui) — отдельный ADR; рефакторинг, включая часть 8, идёт на текущем MUI.

- **Q3.** *(решим в сессии части 3 по удобству для фронтенда; исходная точка — стандартный `ProblemDetails`)*

- **Q5.** *(предложение, подтвердить в сессии части 7)* Миграции применяются отдельным шагом деплоя, не при старте API: `dotnet ef migrations bundle` собирается в образ/артефакт и запускается как pre-deploy шаг (Railway — pre-deploy command; `docker-compose` — одноразовый сервис `migrator`). Миграции пишутся совместимыми с предыдущей версией кода (сначала добавили, потом удалили), чтобы деплой был без простоя.

- **Q7.** *(отложен)* Версионирование API сейчас не вводим: единственный клиент — наш фронтенд, деплоится вместе с backend. Вернуться, когда появится клиент с независимым релизом (мобильное приложение, публичное API) или несовместимое изменение контракта; цена позже невысокая (префикс `/api/v1` + редирект).
